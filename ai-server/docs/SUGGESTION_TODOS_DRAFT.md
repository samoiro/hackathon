# 추천 할 일 만들기 초안 (설계 전용)

대시보드 추천 할 일 섹션(행사 `EVENT`, 원자재 `INGREDIENT`, 부자재 `SUPPLY` 묶음)의 **카드 자체를 어떻게 만드는지** 정한 초안입니다.
강추(상위 3개 고르기)는 [`API_CONTRACT_DRAFT.md`](API_CONTRACT_DRAFT.md) "강추 고르기 (Java)"를 그대로 따르고 여기서 다루지 않습니다.
그림: [`server/docs/suggestion-todos.png`](../../server/docs/suggestion-todos.png)

계약·프롬프트 변경안은 `API_CONTRACT_DRAFT.md`·`PROMPT_DRAFT.md`에 옮겼습니다(아래 "계약·프롬프트에 옮긴 것").

## 한 줄 요약

**Java가 카드 칸(묶음·할 일 유형·품목·근거·순서)을 정하고, LLM은 칸마다 제목·기대 효과·세부 할 일 문장만 씁니다.** 사유(`reason`)와 준비 기한(`dueDate`)은 Java가 근거로 만듭니다.

예전 계약은 LLM이 `task_types` 안에서 유형을 고르고 묶음 안 순서도 정했습니다. 이걸 Java로 옮긴 이유:

- 같은 입력이면 늘 같은 카드가 나옵니다. 테스트 기대값을 문장이 아니라 칸으로 쓸 수 있습니다.
- "묶음 안 순서", "강추 동점 처리(Python이 준 순서)", "해당 없어요 제외"가 모두 Java 안에서 끝납니다.
- Java 검증이 "응답의 `card_id`가 요청에 있는가" 하나로 줄어듭니다. 입력에 없는 `evidence_id`·`item_id`·`task_type`이 나올 수 없습니다.

## 누가 무엇을

| 정하는 것 | 담당 |
| --- | --- |
| 근거 모으기(E·H·W·R·S)와 근거 점수 | Java (기존) |
| 카드 칸: 묶음, 할 일 유형, 품목, 근거 id | **Java** |
| 묶음 안 순서, 묶음당 개수, 제외 | **Java** |
| `reason` (한 줄 사유) | **Java** 템플릿 |
| `dueDate` (준비 기한) | **Java** (강추 행동 마감과 같은 날) |
| `title`, `expected_effect`, `sub_tasks` | **LLM** |
| 강추(`recommended`) | Java (기존) |
| 문장 길이·개수 검증, 1번 재시도 | Python (기존) |

## 카드 칸 만들기 (Java)

### 할 일 유형

행사에만 있던 `task_type`을 세 묶음 모두에 둡니다. `EventTaskType`을 `TaskType` 하나로 바꾸고 아래 값을 더합니다.

| 묶음 | 유형 |
| --- | --- |
| `EVENT` | `STAFFING` 근무 배치 · `STOCK` 재고 · `HOURS` 영업시간 · `PICKUP` 주문·픽업 안내 · `RESERVATION` 예약 안내 · `FACILITY` 매장 정비(**새로**) · `PACKING` 포장 동선 |
| `INGREDIENT` | `PRICE_CHECK` 단가 확인 · `BUY_AHEAD` 미리 주문 · `ORDER_PLAN` 발주량 점검 |
| `SUPPLY` | `RESTOCK` 재고 채우기 · `DISPLAY` 판매 상품 진열 · `ORDER_LESS` 주문 줄이기 |

유형을 두면 Java가 업종·신호에 맞는 할 일만 열어 줄 수 있고(미용실에 식재료 발주가 안 나옴), "해당 없어요" 제외 키로도 씁니다.

### `EVENT` 묶음: 행사 → 시즌 → 날씨

행사 트랙과 같은 순서로 **한 가지 근거만** 씁니다(`EventSource`). 주변 행사(E)가 있으면 E, 없으면 시즌(H), 그것도 없으면 날씨(W), 다 없으면 묶음이 빕니다. 나머지 근거가 여는 다른 유형의 칸은 "카드 채우기"의 후보로만 씁니다(같은 유형은 앞 근거가 차지).

카드 단위는 **할 일 유형 1개**입니다. 행사 여러 건이 같은 유형을 열면 한 카드로 묶습니다("행사 종합").

| 유형 | E 주변 행사 (기존) | H 시즌 | W 날씨 |
| --- | --- | --- | --- |
| `STAFFING` | 음식점·소매점 | – | 음식점이고 `DELIVERY`·`BOTH`, 영향이 비·눈·대설·한파·미세먼지 (배달이 몰릴 수 있음) |
| `STOCK` | 음식점·소매점 | 음식점·소매점 | – |
| `HOURS` | 21시 이후 끝 또는 11시 전 시작 (시간 미상이면 뺌) | 설·추석 (휴무·영업일 안내) | 기상특보 발효 중 |
| `PICKUP` | 음식점, 운영 방식 `STORE`·`BOTH`·모름 | 음식점·소매점, 종류 `HOLIDAY`, 운영 방식이 `DELIVERY`가 아님 (명절 음식·케이크·꽃다발 미리 주문 받기) | – |
| `RESERVATION` | 단체·개인서비스업 | 단체·개인서비스업 | 단체·개인서비스업 |
| `FACILITY` | – | – | 운영 방식이 `DELIVERY`가 아님 (매장 손님이 있음) |
| `PACKING` | 음식점, 축제이거나 17시 이후 끝 | – | – |

- H는 **가게 업종에 그 트리거의 `supply_rule`이 있을 때만** 후보로 봅니다. 미용실에 빼빼로데이가 뜨지 않게 하려는 것입니다(시즌 후보를 고르는 쪽과 맞춰야 함).
- 카드의 근거: 그 유형을 연 근거 전부를 마감 빠른 순으로 최대 3개. 첫 번째가 **대표 근거**이고 제목·사유는 대표 근거로 씁니다.
- `STOCK` 칸은 부자재 묶음에 `kind=STOCK` 카드가 있고 그 카드의 `trigger_evidence_id`가 같은 행사이면 만들지 않습니다("부자재 묶음에 같은 물품이 있으면 그쪽에서 다룹니다"를 Java 규칙으로).

### `INGREDIENT` 묶음

카드 단위는 **고른 원자재 1개**(최대 3개)입니다. 걸린 `ingredient_rule`의 신호 합(강추 점수의 원자재 신호와 같은 값)으로 유형을 정합니다.

| 신호 합 | 유형 | 할 일 뜻 |
| --- | --- | --- |
| −1 이하 (상승) | `PRICE_CHECK` | 거래처 단가 확인, 원가·판매가 다시 보기. `price_stage`가 상승 경계·심각(`ALERT_HIGH`·`SEVERE_HIGH`, `STRONG_DOWN`)이면 대체 재료까지 |
| +1 이상, 김장·설·추석 전 규칙이 걸림 | `BUY_AHEAD` | 값 오르기 전 주문 시기·물량 정하기 |
| +1 이상, 그 밖 (4주 하락 단계·제철·제철 전) | `ORDER_PLAN` | 이번 주 발주량 점검, 제철이면 메뉴·진열에 앞세우기 |
| 0 | `PRICE_CHECK` (채우기 후보) | 거래처 단가만 확인. 근거 점수는 급한 정도·영향 0이라 "카드 채우기"에서 맨 뒤로 밀림. 사유는 4주 변동을 있는 그대로("쌀은 4주 전과 가격이 같아요.") |

- 가격이 `null`이면 가격 규칙은 안 걸리고 제철·명절 규칙만 봅니다. 카드가 나오면 세부 할 일에 "거래처에 현재 단가 묻기"를 넣고 가격 숫자는 쓰지 않습니다.
- 가격 단계가 `STABLE`이고 제철·명절 규칙도 없으면 카드가 없습니다(기존 예시의 쌀). 가격 신호는 4주 변동률 단계(`price_stage`)만 보고 1주 흐름(`trend`)은 점수에 넣지 않습니다.
- 업종: 음식점은 "메뉴 원가", 소매점은 "판매가·진열", 단체·개인서비스업은 "구매"로 말합니다. 업종별 추천 원자재가 없는 서비스업도 직접 고를 수 있어서 막지 않습니다.

### `SUPPLY` 묶음

카드 단위는 **고른 부자재 1개**(최대 2개)입니다. 이번 주 걸린 `supply_rule`이 없으면(화면의 "부자재 정보 없음") 카드가 없습니다.

| 조건 | 유형 | 할 일 뜻 |
| --- | --- | --- |
| `demand`가 `DOWN` | `ORDER_LESS` | 이번 주 주문 줄이기·미루기. V24 기준 `DOWN`은 방학(`SCHOOL_VACATION`, 카페·분식) 규칙뿐 |
| `kind`가 `STOCK` (손님에게 파는 상품) | `DISPLAY` | 재고 확인, 잘 보이는 곳에 진열 |
| 그 밖 (`UP`·`STRONG_UP`, `kind=SUPPLY`) | `RESTOCK` | 남은 수량 확인, `prepare_by`까지 받도록 주문. `STRONG_UP`이면 넉넉히 |

- 한 물품에 규칙이 여럿 걸리면 `prepare_by`가 빠른 것 → `demand`가 큰 것 1개만 씁니다(`SupplyTimingResponse`가 물품당 1개라서).
- 근거는 `[S, trigger_evidence_id]`(트리거 근거가 없으면 `[S]`).
- 운영 방식으로 거르지 않습니다. 사장님이 직접 고른 물품이기 때문입니다.

### 개수와 순서

| 묶음 | 최대 | 순서 |
| --- | --- | --- |
| `EVENT` | 3 | 대표 근거의 행동 마감 빠른 순 → 카드 점수 높은 순 → 유형 순서(위 표의 위에서 아래: 준비에 오래 걸리는 일부터) |
| `INGREDIENT` | 3 | 카드 점수 높은 순 → 1주 변동률 절댓값 큰 순 → 사장님이 고른 순 |
| `SUPPLY` | 2 | `prepare_by` 빠른 순 → 카드 점수 높은 순 → 사장님이 고른 순 |

카드 점수는 강추와 같이 "단 근거 중 가장 높은 근거 점수"입니다. 이 순서가 강추 동점 처리의 마지막 기준("Python이 준 순서")을 대신합니다.

### 카드 채우기

묶음별 최대로 고른 카드가 **6장보다 적으면** 남은 후보로 6장까지 채웁니다. 후보가 모자라면 6장보다 적을 수 있고, 전체는 최대 8장입니다.

- 후보: 묶음 최대를 넘쳐 빠진 칸, 행사 묶음에서 고르지 않은 근거(시즌·날씨)가 여는 다른 유형의 칸, 신호 0인 원자재의 `PRICE_CHECK` 칸
- 순서: 카드 점수 높은 순 → 급한 정도 높은 순 → 묶음 순서(행사 → 원자재 → 부자재)
- 채운 칸도 묶음 안의 후보 순서대로 놓습니다(묶음 안에서는 원래 칸 뒤). 채우기로 들어온 시즌·날씨 근거는 Python 요청과 브리핑 응답(`seasonEvents`·`weather`)에도 넣습니다.
- 채운 칸은 `SuggestionResponse.filled = true`입니다. 강추 후보에서 빠지고, 화면은 중립 태그 "참고"를 붙여 원래 칸과 구분합니다.

### "해당 없어요" 제외

제목으로 거르면 LLM이 같은 일을 다른 말로 다시 쓸 수 있습니다. **제목 대신 칸 키로 거릅니다.**

- 키: `{category}:{task_type}:{item_id 또는 -}`. 예: `EVENT:STAFFING:-`, `INGREDIENT:PRICE_CHECK:12`
- 프론트가 "해당 없어요"를 누를 때 키를 localStorage에 모아 `AnalysisRequest.excludedKeys`(최대 50)로 보냅니다(`excludedTitles` 대신).
- Java는 칸을 고르기 **전에** 제외 키를 빼서, `EVENT`는 다음 유형이 그 자리를 채웁니다. LLM에는 제외 목록을 보내지 않습니다.
- 원자재는 유형까지 키에 들어가서, "배추 단가 확인"을 뺐어도 다음에 배추가 내리면 "배추 발주량 점검"은 나옵니다.

## 문장 규칙

| 필드 | 누가 | 규칙 |
| --- | --- | --- |
| `title` | LLM | 24자 이내. 대상 + 행동 명사형("~확인", "~점검", "~정하기", "~나누기"). `INGREDIENT`·`SUPPLY`는 품목 이름을 넣습니다. 한 응답 안에서 제목이 겹치지 않습니다. |
| `reason` | Java | 40자 이내 사실 한 문장. 대표 근거로 아래 템플릿을 채웁니다. 조사(이/가, 은/는)는 받침으로 고릅니다. |
| `expected_effect` | LLM | 60자 이내 해요체 한 문장, "~수 있어요."로 끝냄. **대표 근거 하나**가 말하는 상황에 대비하는 효과만, 숫자 없이. 매출·손님 수를 말하지 않고, 말할 효과가 없으면 `null`. |
| `sub_tasks` | LLM | 2~3개, 각 24자 이내, 하는 순서대로. **강추면 할 일 목록에 따로 담기므로 카드 없이 읽어도 통하게** 대상(품목·요일·시간)을 넣습니다("단가 묻기" ✗ → "배추 거래처 단가 묻기" ○). 제목을 그대로 되풀이하지 않습니다. |

공통: 숫자는 입력에 있는 것만 씁니다. 날짜·시간은 Java가 `date_label`("11.21(토)")·`peak_label`("15~20시")처럼 화면용 문구로 넘기고 LLM은 그대로 옮깁니다.

### `reason` 템플릿 (Java)

| 근거 | 템플릿 | 예 |
| --- | --- | --- |
| E | `{date_label} {거리}m 거리에서 {분류}이/가 열려요.` (진행 중이면 `…진행 중이에요.`, 2건 이상이면 `…등 행사 {n}건이 있어요.`) | 11.21(토) 650m 거리에서 공연이 열려요. |
| H | `{label}까지 {n}일 남았어요.` (기간 중이면 `{label} 기간이에요.`) | 크리스마스까지 8일 남았어요. |
| W | 특보: `{kind}{level}가 발효 중이에요.` 예보: `{date_label} {영향} 예보가 있어요.` | 11.19(목) 한파 예보가 있어요. |
| R `PRICE_CHECK` | `{품목}이/가 4주 전보다 {pct}% 올랐어요.` (`change_4w_pct`, 가격 단계와 같은 기간) | 배추가 4주 전보다 10.9% 올랐어요. |
| R `ORDER_PLAN` | 하락: `…4주 전보다 {pct}% 내렸어요.` 제철: `{품목}은/는 {m}월 제철이에요.` 제철 전: `{품목}은/는 다음 달부터 제철이에요.` | 돼지고기가 4주 전보다 6.3% 내렸어요. |
| R `BUY_AHEAD` | `{명절}까지 {n}일 남았어요.` | 설까지 18일 남았어요. |
| S `RESTOCK`·`DISPLAY` | `{trigger_label} 준비는 {prepare_by_label}까지예요.` | 공연 준비는 11.18(수)까지예요. |
| S `ORDER_LESS` | `{trigger_label} 기간엔 덜 쓰일 수 있어요.` | 방학 기간엔 덜 쓰일 수 있어요. |

### 유형별 세부 할 일 예 (프롬프트 few-shot)

| 유형 | 세부 할 일 예 |
| --- | --- |
| `STAFFING` | 토요일 15~20시 근무자 정하기 · 주문·수령 담당 나누기 · 근무표 미리 공유하기 |
| `STOCK` | 행사 날 많이 나갈 메뉴 고르기 · 메뉴 재료 남은 양 확인 · 부족한 재료 미리 발주 |
| `HOURS` | 토요일 영업 연장할지 정하기 · 바뀐 영업시간 안내 붙이기 |
| `PICKUP` | 행사 전 미리 주문 안내문 붙이기 · 픽업 시간대 정하기 |
| `RESERVATION` | 행사 날 예약 손님 확인 · 예약 손님께 교통 안내 보내기 |
| `FACILITY` | 입구 미끄럼 방지 매트 깔기 · 입간판 안으로 들이기 |
| `PACKING` | 토요일 포장 대기 자리 정하기 · 포장 주문 받는 순서 정하기 |
| `PRICE_CHECK` | 배추 거래처 단가 묻기 · 배추 들어간 메뉴 원가 보기 · (상승 경계·심각) 배추 대체 재료 알아보기 |
| `BUY_AHEAD` | 배추 주문 마감일 정하기 · 거래처에 배추 물량 묻기 · 배추 보관 공간 확인 |
| `ORDER_PLAN` | 돼지고기 이번 주 발주량 정하기 · 돼지고기 보관 공간 확인 · (제철) 제철 메뉴 안내 정하기 |
| `RESTOCK` | 포장 용기 남은 수량 세기 · 11.18(수)까지 포장 용기 주문 · (`STRONG_UP`) 포장 용기 넉넉히 주문 |
| `DISPLAY` | 생수 재고 확인 · 생수 입구 쪽에 진열 · 생수 가격표 붙이기 |
| `ORDER_LESS` | 테이크아웃 컵 남은 수량 확인 · 이번 주 테이크아웃 컵 주문 줄이기 |

## 피드백 (도움돼요 · 해당 없어요)

카드마다 "도움돼요"·"해당 없어요"를 받아 **사장님 피드백을 반영해 추천이 좋아지게** 합니다. 모델을 다시 학습시키지는 않습니다. 발표에서도 "AI가 학습한다"가 아니라 "사장님 피드백을 반영해 추천이 좋아진다"고 말합니다.

| 단계 | 반영 방식 | 언제부터 |
| --- | --- | --- |
| 1. 내 가게 | "해당 없어요" 키는 `excludedKeys`로 보내 다음 분석에서 그 칸을 뺍니다. "도움돼요" 키는 localStorage에만 두고 본선에서 같은 칸 점수 +1을 검토합니다. | 바로 |
| 2. 모든 가게 | 서버가 업종 × 묶음 × 유형별 "도움돼요" 비율을 집계해, 표가 20개 이상 모인 조합만 강추 점수를 ±1 보정합니다(비율 70% 이상 +1, 30% 이하 −1). 업종별로 "도움돼요"를 많이 받은 문장은 프롬프트 예시로 넣습니다. | 표가 모인 뒤 |
| 3. 모델 재학습 | 하지 않습니다. 데이터가 수천 건은 필요합니다. | — |

- 저장: `suggestion_feedback` 테이블(V25). 분석 1건의 카드 1장에 1표, 다시 누르면 표를 바꿉니다. 카드 키와 묶음·유형·품목 값이 어긋나면 DB가 거부합니다.
- API: `POST /api/analysis/{id}/feedback` `{ "cardKey": "INGREDIENT:PRICE_CHECK:12", "vote": "HELPFUL" }` → 204. `cardKey`는 `SuggestionResponse.cardKey`를 그대로 보냅니다.
- 로그인이 없어 장난·중복 표를 완전히 막을 수는 없습니다. 1표 제한과 최소 20표 조건으로 영향을 줄입니다.
- 사전 준비 범위: 테이블·DTO까지 만들었고, 집계·점수 보정·API 구현은 본선에서 합니다.

### 누른 뒤 뜨는 팝업

화면 아래에서 올라오는 작은 팝업(토스트)으로 띄웁니다. 다른 일을 막지 않고, 디지털 기기에 익숙하지 않은 사장님이 읽을 수 있게 5초 동안 보여 준 뒤 사라집니다. 눌러서 바로 닫을 수도 있습니다.

| 누른 버튼 | 토스트 제목 | 토스트 내용 | 카드에 남는 것 |
| --- | --- | --- | --- |
| 도움돼요 | 의견 고마워요! | 사장님 의견을 반영해 다음 추천을 더 잘 맞춰 드릴게요. | 버튼이 눌린 상태 |
| 해당 없어요 | 알려 주셔서 고마워요 | 사장님 의견을 반영해 다음 추천을 더 잘 맞춰 드릴게요. | "해당 없어요로 표시했어요. 다음 브리핑부터 이 할 일은 빼 드릴게요." + 되돌리기 |

- 토스트는 고맙다는 말과 좋아지는 점만 말하고, 무엇이 바뀌는지와 되돌리기는 카드에 둡니다. 같은 말을 두 군데 띄우지 않기 위해서입니다.
- "되돌리기"는 표를 지우고 `excludedKeys`에서 키를 뺍니다. 실수로 눌러도 바로 돌릴 수 있어야 합니다.
- Figma: 사모이로 › 📱 Screens › Mid-fi BI·CI 톤 적용안의 상태 모음에 "토스트 · 도움돼요를 누른 뒤", "토스트 · 해당 없어요를 누른 뒤"를 기존 "토스트 · 네트워크 끊김" 스타일로 넣었습니다.
- 지킬 것: 실제로 일어나는 일만 말합니다("빼 드릴게요", "반영해"). "AI가 학습해요", "정확도가 올라가요"처럼 확인할 수 없는 말은 쓰지 않습니다. 이모지 없이 해요체로 씁니다.
- 다른 안: 토스트 내용 "좋은 의견 고마워요! 더 잘 맞는 추천에 반영할게요." (조금 더 따뜻함)

### 강추 할 일 정리 (이미 했어요 · 해당 없어요)

예전 규칙은 "AI 강추는 할 일에서 삭제 불가"였습니다. 심사에서 "지울 수 없는 강추가 부담"이라는 의견이 나와, **강추도 이유를 보여 주고 사장님이 정리할 수 있게** 바꿉니다. 할 일은 그대로 브라우저 localStorage `todos:{analysisId}`에 둡니다.

| 동작 | 단위 | 하는 일 |
| --- | --- | --- |
| 담기 | 카드 | 강추 카드의 `subTasks`를 대시보드를 처음 열 때 할 일로 담습니다(기존). 항목: `{ id, text, cardKey, done }`, 직접 추가한 할 일은 `cardKey`가 `null` |
| 이유 보기 | 카드 | 할 일 목록에서 강추 항목은 `cardKey`로 묶고, 묶음 머리에 `title`·`reason`·준비 기한(`dueDate` "11.21(토)까지", `null`이면 "이번 주 발주 전")을 보여 줍니다. |
| 이미 했어요 | 세부 할 일 | `done = true`. 목록에 남고 다시 누르면 풉니다. 피드백은 보내지 않습니다. |
| 해당 없어요 | 카드 | 카드의 "해당 없어요"와 같습니다: 피드백 `NOT_RELEVANT`를 보내고, `cardKey`를 `excludedKeys`에 더하고, 그 `cardKey`의 할 일을 목록에서 뺍니다. 되돌리기는 셋을 모두 되돌립니다. |
| 삭제 | 세부 할 일 | 직접 추가한 할 일만. 강추 항목은 삭제 대신 "해당 없어요"로 정리해서, 뺀 이유가 다음 추천에 반영되게 합니다. |

같은 분석 안에서 강추를 다시 고르지 않습니다. 뺀 카드는 다음 분석부터 `excludedKeys`로 빠집니다.

## 계약·프롬프트에 옮긴 것 (2026-11-21)

계약 변경안과 프롬프트 변경안은 [`API_CONTRACT_DRAFT.md`](API_CONTRACT_DRAFT.md)·[`PROMPT_DRAFT.md`](PROMPT_DRAFT.md)에 옮겼습니다. 요청·응답 JSON과 프롬프트 전문은 그쪽이 기준입니다.

- 요청: `cards` 새로, `season_events`·`weather` 새로, `events[].task_types` 삭제, `start`·`end`·`peak_time` → `date_label`·`peak_label`, `raw_materials[]`에 `price_stage`·`signals`·`consecutive_weeks` 새로(`weekly_prices` 뺌), `supplies[]`에 `kind`·`trigger_label`·`prepare_by_label`, `excluded_titles` 삭제.
- 응답: `card_id`·`title`·`expected_effect`(`null` 가능)·`sub_tasks`만.
- 묶음 이름 `RAW_MATERIAL` → `INGREDIENT`.
- 기대 효과는 대표 근거(`evidence_ids[0]`) 하나에 기대고 숫자를 쓰지 않습니다. 계약 "기대 효과의 근거".
- 준비 기한 `dueDate`는 Java가 붙입니다. 계약 "준비 기한 (Java)".

### Java DTO 변경

| 대상 | 변경 |
| --- | --- |
| `EventTaskType` | **반영함:** `TaskType`(13개)으로 바꿨습니다. |

| `SuggestionResponse.expectedEffect` | **반영함:** 대표 근거 기준, 숫자 없음, 근거로 말할 효과가 없으면 `null`. |

## 예시: 성수동 한식당 (`BOTH`, 기준 11.17)

입력은 계약 초안의 요청 예시와 같습니다: 서울숲 음악회(E1, 공연 650m, 11.21(토) 16~19시), 배추(R1, 4주 10.9% 상승, `ALERT_HIGH`), 돼지고기(R2, 4주 6.3% 하락, `WATCH_LOW`), 쌀(R3, `STABLE`), 포장 용기(S1, 공연, 11.18(수)까지), 일회용 수저(S2, 공연, 11.19(목)까지).

| 칸 | 묶음 · 유형 | 근거 | Java `reason` · `dueDate` | LLM `title` | LLM `sub_tasks` |
| --- | --- | --- | --- | --- | --- |
| C1 | EVENT · STAFFING | E1 | 11.21(토) 650m 거리에서 공연이 열려요. · 11.21 | 토요일 공연 시간대 역할 나누기 | 토요일 15~20시 근무자 정하기 · 주문·수령 담당 나누기 · 근무표 미리 공유하기 |
| C2 | EVENT · STOCK | E1 | (같음) | 공연 날 식재료 재고 확인 | 토요일 많이 나갈 메뉴 고르기 · 메뉴 재료 남은 양 확인 · 부족한 재료 미리 발주 |
| C3 | EVENT · PICKUP | E1 | (같음) | 공연 전 미리 주문 안내하기 | 미리 주문 안내문 붙이기 · 토요일 픽업 시간대 정하기 |

| C7 | SUPPLY · RESTOCK | S2, E1 | 공연 준비는 11.19(목)까지예요. · 11.19 | 일회용 수저 추가 주문 | 일회용 수저 남은 수량 세기 · 11.19(목)까지 일회용 수저 주문 |

- E1이 연 유형은 `STAFFING`·`PICKUP`·`PACKING`·`STOCK`입니다. 마감·점수가 같아서 유형 순서로 3개(`STAFFING`·`STOCK`·`PICKUP`)를 고르고 `PACKING`은 빠집니다.

- (C2·C3)은 C1과 같은 사유·기한입니다. 기대 효과 예시는 [`PROMPT_DRAFT.md`](PROMPT_DRAFT.md) "예시"에 있습니다.
- 기존 프롬프트 예시처럼 같은 물품으로 카드 2장("재고 확인" + "추가 주문 시점 확인")을 만들지 않고, 한 카드의 세부 할 일로 넣습니다. 같은 근거 카드는 강추가 1개뿐이라 둘째 카드는 늘 묻히기 때문입니다.

## 정한 것 (2026-11-21)

- 원자재 묶음 이름은 `INGREDIENT`로 통일합니다(계약·프롬프트 반영함).
- "해당 없어요" 제외는 `excludedTitles` 대신 `excludedKeys`로 합니다(반영함).
- 심사 피드백 반영: 카드에 준비 기한 `dueDate`, 기대 효과는 대표 근거 기준(숫자 없음, 없으면 `null`), 강추도 "이미 했어요"·"해당 없어요"로 정리.

## 남은 결정

- 원자재 신호 상쇄: 제철(+2)인데 4주 상승 경계·심각(−2)이면 합 0이라 카드가 사라집니다. 지금 강추 규칙을 따랐지만, 단가 확인은 필요한 상황이라 "합이 0이어도 상승 규칙이 걸리면 `PRICE_CHECK`"로 바꿀지 정해야 합니다.
- 시즌(H) 후보를 업종에 그 트리거 규칙이 있을 때로 제한할지 (시즌 후보를 고르는 쪽과 맞춤)
- 행사 트랙이 E인데 부자재가 날씨·시즌 규칙으로 걸리면, W·H 근거를 `EVENT` 카드 없이 근거 목록에만 넣을지
- `PACKING`과 운영 방식: 기존 프롬프트는 "STORE면 포장 준비를 제안하지 않는다"인데 유형 표는 `STORE`에도 `PACKING`을 엽니다. 여기서는 `STORE`를 "매장(포장 포함)"으로 보고 배달 준비만 막았습니다.
- `EVENT` 유형 순서(준비에 오래 걸리는 일부터)와 `FACILITY`를 새 유형으로 둘지
